# 议题

议题（ticket）是本系统的核心对象：一个议题由模板生成，带动态表单、正文、状态、标签、受理人、上下文信息、评论、附件与审计时间线。

## 创建议题

入口为 `/tickets/new`，分两步：

1. 选择模板。列表只显示启用中的模板（`enabled: false` 的模板不会出现，也不能通过接口创建议题）。
2. 填写动态表单。字段由模板 `body` 定义，支持单行文本、多行文本、下拉选择、选择或输入、复选框、玩家选择与 Markdown 说明块，字段语义与校验见 [模板字段](../template/fields.md)。

提交时的规则：

- 标题必填，最长 200 字符；若模板配置了 `title_prefix`，前缀会自动加到标题前（重复输入的前缀会被去掉后重新拼接）。
- 表单值统一以字符串提交，复选框用英文逗号分隔；下拉框提交选项的真实值即可，历史上的「label|value」写法仍会被归一化。
- 附件：先在编辑区粘贴、拖拽或选择文件上传，前端把临时 URL 替换为 `/api/attachments/<id>`，提交时把这些附件 ID 放进 `attachmentIds`；附件必须属于当前用户且处于 `pending` 状态，否则整次创建失败（`附件不存在或无权关联`）。
- 可见性由模板的 `hidden` 决定：`true` 固定隐藏、`false` 固定公开、`optional` 时创建者必须二选一，未提交可见性会报错 `此模板必须选择议题可见性`。
- 来源服务器 `serverId` 只接受 staff / admin（或可信的 Minecraft 会话）提交，玩家传入会被拒绝（`只有管理组或可信 Minecraft 会话可以指定来源服务器`），且服务器必须存在。网页创建页不提供来源服务器选择，该字段主要由游戏内会话与管理接口使用。

模板另外可以配置默认受理人与默认标签：创建时会自动指派给这些 staff/admin 用户（无效 ID 会被跳过）并自动挂上标签，指派成功会给被指派者发邮件。

## 列表与筛选

议题列表在 `/`，搜索框支持带键的筛选词，也可以直接调 `GET /api/tickets` 用查询参数：

| 参数 | 含义 |
| --- | --- |
| `statuses` | 状态，逗号分隔或重复参数，取值 `open` / `in_progress` / `closed` / `invalid` |
| `type` | 模板名（不是显示名称） |
| `authorId` | 作者用户 ID |
| `authorName` | 作者用户名，模糊匹配 |
| `serverId` | 来源服务器记录 ID |
| `serverName` | 来源服务器名称或别名，精确匹配 |
| `hasServer` | `true` 只看游戏内提交、`false` 只看网页提交 |
| `labelId` | 标签标识符 |
| `search` | 标题或正文包含该关键字 |
| `page` / `pageSize` | 分页，默认 1 / 20，页大小上限 100 |

排序固定为创建时间倒序。列表只返回当前访问者可见的议题；当访问者无权查看某议题的上下文时，返回结果里的 `gameContext` 会被置为 `null`。

前端搜索框的筛选键与接口参数的对应关系是：`status:`→`statuses`、`type:`→`type`、`label:`→`labelId`、`from:web|minecraft|minecraft:<server>`→`hasServer` 或 `serverId`/`serverName`、`author:`→`authorName`，剩余纯文本合并进 `search`。

## 详情页构成

`/tickets/:id` 包含：

- 标题与正文：正文按 Markdown 渲染；作者与管理组可以就地编辑标题、正文。
- 状态卡片：展示当前状态；staff/admin 可以点击其他状态直接切换。
- 可见性卡片（仅管理组可见）：在「所有人可见」与「仅发起者与管理组可见」之间切换。
- 受理人卡片：展示当前受理人，管理组可以打开选择器调整（候选范围是 staff 与 admin）。
- 标签卡片：管理组可以添加或移除标签，模板自带的标签在创建时已自动挂上。
- 附加信息：世界、坐标、游戏模式与来源服务器，用于从游戏内提交的议题。
- 完成钩子：状态进入 `closed` / `invalid` 后出现的决策卡片。
- 时间线：评论与审计记录按时间合并展示；审计里的标题、正文类修改会合并约 15 秒内的连续编辑为一条记录，避免刷屏。
- 附件列表：展示此前上传并已关联到该议题的文件。

## 状态与合法转换

状态只有四个值：`open`、`in_progress`、`closed`、`invalid`。合法转换是：

| 当前状态 | 可转到 |
| --- | --- |
| `open` | `closed` |
| `in_progress` | `closed` |
| `closed` | `open` |
| `invalid` | `open` |

约束细节：

- 玩家只能把议题改成 `open` 或 `closed`，且仅限自己的议题；改成其他值返回 `玩家只能开启或关闭自己的议题`。
- 玩家不能把 `invalid` 议题重新打开（`无效议题只能由管理员或管理组重新打开`）。
- `open`/`in_progress` 才能关闭（`只有开放或处理中的议题可以关闭`）；只有 `closed` 才能重新打开（`只有已关闭的议题可以重新打开`）。
- 管理组通过 `PATCH /api/tickets/:id` 可以直接写入任意状态值，不受上面两条玩家限制；但专用的 `/close`、`/reopen` 端点对管理组同样要求满足前置状态。
- 状态变更使用乐观并发：若两次修改同时发生，后到者会收到 409 `议题状态已被其他请求修改`，刷新后重试即可。
- 关闭与标记无效时写入 `closedAt`；重新打开会清空该时间。

## 可见性与上下文

两条独立规则：

- 议题可见性（`hidden`）：隐藏议题只对作者本人和 staff/admin 可见；其他人（含未登录访问者）查询或打开该议题会得到「议题不存在」，列表里也不会出现。只有管理组可以修改这个开关，修改会记入审计。
- 上下文可见性（`allowContextView`）：从游戏内创建议题时可以回答「是否允许普通用户查看此议题的附加信息」。回答「否」后，普通用户看到的 `gameContext` 与来源服务器会被抹掉；作者本人与 staff/admin 始终可见。

此外，启用站点设置里的 `requireLogin` 后，未登录访问者连公开议题也无法查看。

## 完成钩子

模板可以在 `closed` 或 `invalid` 事件上配置完成钩子。状态进入对应事件时：

- 需要人工决策的钩子会生成一条「待完成」记录，并在议题详情页展示卡片，列出决策字段（文本、下拉、多选、玩家选择等），必填项未填写时不允许提交。
- staff/admin 可以「确认并执行动作」提交结果，也可以选择「不做决策」跳过；两个操作分别对应 `POST /api/tickets/:id/completion-hooks/:hookId/complete` 与 `.../skip`，都要求 staff 及以上角色。
- 提交后，模板中配置的命令或 MiniMessage 会通过在线服务器执行，执行结果（成功/失败与错误信息）回显在卡片里；无法投递的记录稍后可由管理员重试。
- 决策卡片的可见性由模板决定：公开卡片在决策完成后对所有人可见，隐藏卡片始终只有管理组可见。
- 若议题带有来源服务器，且关闭动作会触发控制台命令类钩子，则玩家自行关闭会被拒绝（`包含控制台命令的完成操作必须由管理员或管理组确认`），需要管理组操作。

## 编辑、指派与标签

- 标题：`PATCH /api/tickets/:id/title`，作者或管理组可调用，标题 1~200 字符，修改记入审计。
- 正文：`PATCH /api/tickets/:id/body`，同样限作者或管理组，正文不能为空。
- 受理人：`PUT /api/tickets/:id/assignees`，需要 staff 及以上，提交的是完整的受理人列表（会覆盖旧值）；ID 必须去重且都指向 staff/admin，否则报 `受理人必须是存在的 staff 或 admin 用户`；新增的受理人会收到邮件提醒。
- 标签：`POST /api/tickets/:id/labels` 与 `DELETE /api/tickets/:id/labels/:labelId`，需要 staff 及以上，标签标识符必须是已存在的标签。
- 状态：`PATCH /api/tickets/:id`（`status`）或语义化的 `/close`、`/reopen`；`hidden` 只能由管理组通过同一个 `PATCH` 修改。
